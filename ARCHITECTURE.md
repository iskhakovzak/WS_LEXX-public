# WS_LEXX: архитектурные принципы

Документ задаёт правила, по которым развивается код. Каждое правило проверяется автоматически (линтер, тест, скрипт-«храповик» в CI) или чеклистом ревью. Существующий долг фиксируется базовым списком (baseline). Список может только сокращаться: новый код сразу пишется по правилам, старый подтягивается по мере касания.

Основа: исследование 2026-10-17 (frontend, backend, data, tooling/security), отчёты в `docs/research/`.

---

## 0. Сквозные правила

1. **Сделки приходят только из PropReports.** Ручного создания, импорта и редактирования денег сделки нет ни в UI, ни в API. Вручную пользователь пишет только плейбук, планы, журнал, заметки и разметку сделок (сетап, теги, оценки).
2. **Один способ сделать одну вещь.** Один HTTP-клиент, один формат ошибки, один реестр фоновых задач, один источник схемы БД, один модуль форматирования, один способ проверить права.
3. **Храповики, а не «большой взрыв».** Любое новое правило вводится с baseline. CI падает, если долг вырос.
4. **Ошибка лучше тихого неверного поведения.** Сервер не стартует при битой конфигурации или упавшей миграции. 404 от API — это баг, а не повод для запасной ветки.
5. **Три языка: RU, EN, UZ (латиница).** Любой текст, который видит человек, идёт через i18n (`src/i18n`, серверный `src/i18n`). Торговая база (тикеры, P&L, R, MAE/MFE, OPG/MOC/…, Long/Short) и пользовательский контент не переводятся. В БД хранятся коды и параметры, а не готовый текст.
   Имена людей: хранимое имя (кириллица) — идентификатор везде (параметры API, URL, фильтры, ключи); показывается через `personName()` (web `src/i18n/person-name.ts`) / `personNameFor(name, lang)` (API `lib/people/latinNames.ts`): в EN/UZ — латинское имя `users.name_latin`, если задано, иначе хранимое; в RU — всегда хранимое (решение владельца 2026-10-18).
6. **Время.** Моменты хранятся в `timestamptz` (UTC). «Торговый день» — это дата Нью-Йорка (`nyDate`). `CURRENT_DATE` и `::date` от момента запрещены.
7. **Деньги.** В БД `numeric` с явной точностью. В UI торговый формат одинаков во всех языках: `$1,234.56`, `+0.21R`, цены с точкой.

## 1. Frontend (`artifacts/edge-tracker`)

### Слои (пути не переименовываем)
```
src/app/                 App, провайдеры, query-client, ЕДИНАЯ таблица маршрутов (path, loader, title, nav, roles)
src/pages/<route>.tsx    тонкие страницы: читают URL и собирают фичи (≤ 250 строк)
src/components/<feature>/  фича: api.ts (queryOptions и мутации), model.ts (чистая логика), *.tsx
src/components/shared/   доменные виджеты нескольких фич: people, charts, trade
src/components/ds/       дизайн-система (шкала токенов в начале index.css)
src/components/ui/       только используемые shadcn-примитивы
src/lib/                 чистый код без React: format/, dates, trade-math, permissions, url-state
src/lib/api/             http.ts (единственный клиент), errors.ts, keys.ts, invalidate.ts
src/hooks/  src/i18n/
```

### Правила
1. **Направление зависимостей:** `lib` ← `ui/ds` ← `shared` ← `<feature>` ← `pages` ← `app`. Фича не импортирует другую фичу, общее поднимается в `shared`. Проверка: dependency-cruiser с baseline.
2. **Один HTTP-клиент:** `lib/api/http.ts` поверх `customFetch` из сгенерированного клиента. Он бросает единственный `ApiError {status, code, message}` и сам добавляет `X-Lang`. `fetch(` вне `lib/api/**` запрещён (линтер). Исключения — стримы и blob через `http.raw()`.
3. **Запросы оформляются как `queryOptions`-фабрики в `api.ts` своей фичи.** Ключ строится как `[domain, ...scope, params]`, домен берётся из закрытого списка `lib/api/keys.ts`. У одного эндпоинта одна фабрика.
4. **Инвалидация декларативная:** запрос объявляет, от каких данных зависит (`meta.deps: ["trades"]`), мутация вызывает `invalidateDomain("trades")`. Ручных списков префиксов нет.
5. **Свежесть данных задаётся константами** `STALE.live/short/long/static` и `POLL.*`, магических чисел нет.
6. **Форматирование только из `lib/format` и `i18n/format`.** `new Intl.*` с локалью интерфейса на уровне модуля и строка `"ru-RU"` в коде запрещены (храповик).
7. **Состояние:** серверные данные живут только в Query. Состояние в URL — через один `useSearchParam`. Сохраняемое состояние интерфейса — через один `usePersistentState` с ключом пользователя. Копировать данные запроса в `useState` нельзя.
8. **Асинхронный UI:** `QueryState` либо три ветки с `ErrorState`. Голый спиннер на месте секции недопустим.
9. **Формы** больше чем из 3 полей делаются на react-hook-form + zod.
10. **Размер:** функция компонента ≤ 300 строк, файл ≤ 600 строк (baseline).
11. **Линтер:** typescript-eslint, react-hooks (с правилами React Compiler), @tanstack/query, jsx-a11y. Тесты тоже проходят проверку типов.
12. **Запасных веток «для старой версии API» нет.**

## 2. Backend (`artifacts/api-server`)

### Структура (переход по фичам, после волны перевода)
```
src/features/<feature>/<feature>.routes.ts   только HTTP: разобрать, проверить права, вызвать сервис, ответить
src/features/<feature>/<feature>.service.ts  бизнес-правила и транзакции, без req/res
src/features/<feature>/<feature>.sql.ts      SQL и типы строк
src/domain/*         чистые движки (tradeMath, rulesEngine, …)
src/integrations/*   http.ts (таймауты, ретраи, логирование), ai.ts, marketData/*, propreports/*
src/jobs/registry.ts единый реестр фоновых задач
src/config.ts        env, проверенный zod на старте
```

### Правила
1. **Контракт:** каждый обработчик объявляет zod-схемы для `params`, `query` и `body` через один хелпер `route({…}, handler)`. Читать `req.body` и `req.query` вне него запрещено (baseline).
2. **Одна форма ошибки:** `{ error, code, details? }`. Обработчик бросает `AppError(code, …)`, тело ошибки пишет только error-middleware. Текст переводится по `code` на язык запроса. Ответ `res.status(4xx|5xx).json(` вне `lib/http` запрещён (храповик).
3. **Контракты API пишутся кодом на zod** в общем пакете `lib/api-contracts`. Сервер ими валидирует, клиент берёт из них типы. OpenAPI генерируется из контрактов, orval заморожен на текущих путях.
4. **Права только через capabilities из матрицы** (`requireCap` / `can` / `scopeFor`). Проверять `authUser.role` напрямую нельзя. Academy входит в матрицу. Тест: каждая capability используется, у каждого изменяющего маршрута есть проверка.
5. **Большие коллекции** отдаются страницами или потоком, без явного экспорта ответ не больше 2 МБ. JSON сжимается общим middleware.
6. **Транзакции** — `withTx`. У пула заданы `statement_timeout`, `idle_in_transaction_session_timeout` и обработчик ошибок.
7. **Фоновые задачи** — только через реестр: расписание в NY-времени, advisory-lock на каждый запуск, история в `job_runs`. Побочных эффектов при импорте модуля нет.
8. **GET никогда ничего не меняет:** без записей и уведомлений.
9. **Внешние вызовы** идут только через `integrations/http.ts` (таймаут, ретрай для идемпотентных запросов, лог). AI — только через `integrations/ai.ts`.
10. **`process.env`** читается только в `config.ts`. Секреты не выводятся друг из друга.
11. **Отказоустойчивость:** при `uncaughtException` процесс логирует и выходит. SIGTERM запускает плавную остановку. Есть отдельные проверки `/healthz` и `/readyz`.
12. **Логи:** `logger.error({ err }, msg)`. Пароли, PIN и токены не пишутся ни на каком уровне.

## 3. Данные (PostgreSQL)

1. **Одна история миграций:** нумерованные неизменяемые SQL-файлы в `migrations/` применяются раннером на старте под advisory-lock. Если миграция упала, сервер не стартует. DDL вне `migrations/` запрещён (CI-grep). Снимок схемы закоммичен, CI сверяет его с чистой сборкой.
2. **Expand → backfill → switch → constrain → contract.** `lock_timeout` в каждой миграции. Индексы на больших таблицах создаются `CONCURRENTLY`.
3. **Исправления данных — тоже миграции:** разовые и записанные в истории. На старте сервера нет «ремонтов».
4. **Люди:** каждая колонка со ссылкой на человека имеет FK на `users`: сначала `users(name) ON UPDATE CASCADE`, позже, если понадобится, переход на `user_id`. Системные акторы (`system`, `import-script`) заведены как неактивные пользователи. Переименование — одна операция через специальный эндпоинт: каскад, сброс токенов, аудит. `name_latin` нужен только для отображения и поиска.
5. **Перечисления хранятся как text + CHECK.** Нормализация выполняется при записи, а не при каждом чтении. Ярлыки интерфейса и переведённый текст в БД не хранятся.
6. **JSON** используется для документов и снимков. Поле, которое участвует в WHERE/ORDER/GROUP, становится колонкой.
7. **Удаление:** пользовательский контент удаляется мягко (`deleted_at`), архив оформляется через `archived_at`. Жёсткое удаление допустимо только для связок и кэшей.
8. **Аудит** изменений пользователей, ролей, прав, лимитов и денег пишется в той же транзакции.
9. **Кэши** — таблицы `*_cache` с TTL и ночной чисткой, их данные не попадают в бэкапы.
10. **Бэкапы:** ежедневно в фиксированный час по Нью-Йорку, дамп идёт потоком, шифруется и хранится вне основного провайдера. Раз в месяц автоматически проверяется восстановление. Об ошибке приходит оповещение.

## 4. Инструменты, безопасность, поставка

1. **`pnpm verify`** = lint + typecheck (включая тесты) + test + build. CI (GitHub Actions) запускает ровно это плюс gitleaks, audit, permissions parity и храповики (i18n, z-index, размеры, «ru-RU»).
2. **Biome:** сначала только линтер и только по изменённым файлам. Форматирование — одним коммитом после волны перевода, его SHA вносится в `.git-blame-ignore-revs`.
3. **Версии** Node и pnpm закреплены. Общие зависимости живут в catalog. Обновления зависимостей — Dependabot; уязвимости high/critical в runtime блокируют CI.
4. **Секреты** хранятся только в Replit Secrets или `.env.local`. Дампов и выгрузок в рабочей папке нет.
5. **SQL** получает значения только через `$n`. Идентификаторы берутся только из типизированных карт. `dangerouslySetInnerHTML` вне `ui/chart.tsx` запрещён.
6. **Вход:** лимит попыток считается по IP + имени, неудачные попытки блокируют аккаунт и пишутся в аудит. Есть CSP и лимит размера тела запроса (по умолчанию 256 КБ). SPA и API отдаются одним Express-процессом.

## 4a. UX-принципы (обязательны для любого экрана)

Применяются при каждом изменении интерфейса. При ревью экрана проверяется каждый пункт.

1. **Замыкание (closure): следующий элемент выглядывает.** Горизонтальные ряды (плитки KPI, Big 7, галереи, карусели уроков, ленты карточек, переполненные табы) не обрезаются ровно по краю. Следующий элемент видно примерно на треть, чтобы было понятно, что дальше есть ещё. Скролл-контейнеры показывают край, а не прячут его.
2. **Фигура и фон: тусклое всё, что за фокусом.** Диалог, шторка, палитра команд и режим фокуса (разбор, тренировка, реплей) затемняют фон заметно (примерно 2.5:1 против 17:1 без затемнения), а панель в фокусе поднята над фоном. Внутри страницы активная строка или карточка выделяется, соседние приглушаются, если это помогает.
3. **Слепота к баннерам: важное не похоже на рекламу.** Стоп по риску, нарушения, лимиты, «нужен чек-лист», ждущий разбор, ошибки синхронизации показываются рядом с действием, которого касаются. Оформление — семантический цвет, иконка и короткий текст. Нельзя делать их яркими градиентными плашками сверху. Декоративные блоки (цитата дня, промо-подсказки) не спорят за внимание с рабочими сигналами.
4. **Закон Паркинсона: заполняем то, что уже знаем.** Формы подставляют известное: сетап из сделки (тикер, сторона, дата, стратегия, сессия), дату плана (следующая сессия), автора, трейдера и дату заметки, последнего выбранного трейдера, фильтры, шаблоны целей и отзывов. Цель — минимум нажатий (30 → 7). Обязательных полей как можно меньше, остальное раскрывается по запросу.
5. **Связность: шаги одного процесса связаны.** Закрытие дня → разбор → уведомление; сделка → разбор дня → дневник → сетап; вход плейбука → новый сетап → пример; путь в Академии; смена пароля после входа. Шаги видны (степпер, прогресс, «следующий шаг»), визуально сгруппированы и ведут друг к другу ссылками. Человек не теряет, где он и что дальше.
6. **Перегрузка выбором: меньше вариантов сразу.** Сразу видны 3–5 главных действий, фильтров или пресетов, остальное — под «Ещё». У списка есть разумная сортировка и вид по умолчанию. Опциональные секции скрыты, пока их не включат. В меню и палитре сначала идут частые действия.

## 6. Принятые решения

- Сырой SQL — стандарт, Drizzle постепенно убираем, `drizzle-kit push` запрещён.
- Контракты API — общий пакет zod-схем, OpenAPI генерируется из них, orval заморожен.
- Папку `components/` не переименовываем в `features/` на фронте: правила работают на текущих путях.
- Раннер миграций — свой, ~100 строк (`schema_migrations` + `pg_advisory_lock` + упорядоченные SQL-файлы, падение = отказ старта), без новой зависимости; baseline на production помечается как уже применённый. Старый `runMigrations` остаётся no-op на 1–2 релиза.
- Люди: FK по имени с `ON UPDATE CASCADE` и поддерживаемое переименование. Полный переход на `user_id` отложен, на 30 пользователей он не окупается.
- Системные акторы заводятся как неактивные строки `users`.
- Пользовательский контент удаляется только мягко.
- Бэкапы делаются ежедневно, храним 14 дневных + 8 недельных, кэши не бэкапятся.
- Dependabot, а не Renovate: работает без установки GitHub App.
- Токен входа: bearer на 7 дней со скользящим продлением + CSP; `?access_token` в URL убран; `jwt.verify` с явным алгоритмом. httpOnly-cookie не делаем: для внутреннего приложения с CSP не окупается.
- Канонические форматы чисел:
  - деньги `$1,234.56`, со знаком `+$1,234.56`, компактно `$1.2K`;
  - проценты `+1.23%`, R `+0.21R`;
  - количества и даты — по локали языка.

### Решения владельца (2026-10-17)

- **Вход:** список имён до входа скрыт; имя вводится в поле с многоязычным поиском (кириллица/латиница/узбекская латиница). Трейдеры входят по PIN с блокировкой аккаунта после 5 ошибок; кураторы и админы — по паролю от 10 символов. Лимит попыток считается по IP + имени.
- **Свой секрет у каждого (2026-10-18):** выданный секрет (первый вход, сброс админом, стартовый `src/db/tools/starting-secret.ts`) помечается `users.must_change_secret`; после входа с ним API разрешает только смену, пока человек не задаст свой. Общий стартовый секрет (например `000000`) раздаётся только когда люди входят сразу: вход по имени, и кто первым ввёл чужое имя, тот и задаст пароль.
- **Ошибки приложения** собираются внутри системы: таблица в БД, страница «Ошибки» в админке, оповещение админам в Telegram. Сторонние сервисы не используются.
- **Миграции данных на проде разрешены:** `breakeven→be`, `Active→watching`, удаление ссылок на несуществующие сделки, удаление пустой `playbook_trade_ideas`, разовые «ремонты» на старте убираются. Каждое изменение — отдельная миграция с логом числа строк.
- **История git не переписывается:** владелец меняет секреты (Telegram-токен, PIN и пароли, `ADMIN_PASSWORD`, `PLAYBOOK_PASSWORD`, `JWT_SECRET` с отдельными `MEDIA_TOKEN_SECRET` и `TELEGRAM_WEBHOOK_SECRET`), в CI работает gitleaks.
